## 1. Where a transaction is built or sent

There is exactly **one** place customer-payment calldata is constructed, and **one** place
it is signed/broadcast. This is good — a single chokepoint.

| # | What | File:line | Notes |
|---|---|---|---|
| 1 | **Build** ERC20 `transfer` calldata + append attribution suffix | `backend/src/routes/invoices.ts:104-107` (POST) and `:130-138` (GET) | The only calldata construction. `appendAttribution()` is applied in BOTH. |
| 2 | **Sign/broadcast** the payment | `frontend/components/CheckoutClient.tsx:82-90` | `eth_sendTransaction` with `data` taken verbatim from the backend intent. Frontend never builds calldata itself. |
| 3 | Wallet **sign-in** (no money) | `frontend/components/WalletConnect.tsx:15` | `personal_sign` only — not a transaction. |
| 4 | ERC-8004 **registration** tx | `register.js:40` (`sdk.registerIdentity()`) | Sent from the agent wallet. **Does NOT currently carry the attribution tag.** |

**Agent (Telegram) and MCP build NO transactions.** `agent/src/tools.ts` is an empty stub;
the bot forwards to `backend/src/routes/agent.ts`, and MCP (`mcp/src/index.ts`) only calls
backend REST endpoints. Neither signs or sends on-chain.

Consequence for Stage 4 ("tag every transaction path"): customer payments are already
single-chokepoint tagged. The one untagged on-chain path is the **agent-wallet ERC-8004
registration** (`register.js`), which Stage 7 must tag.

## 3. How payments are verified

Verification is strong and independent of the client. `backend/src/services/paymentVerifier.ts`
is the single source of truth; the frontend/bot/MCP can only submit a tx hash.

Checklist enforced (`paymentVerifier.ts` + `invoices.ts /verify-payment`):
1. Tx exists and `status === 1` on-chain.
2. Chain is Celo mainnet (42220).
3. A `Transfer` log of the **expected token** to the **invoice wallet** is present.
4. Amount matches/exceeds invoice (handles PARTIALLY_PAID / PAID / OVERPAID aggregation).
5. ≥ 12 confirmations.
6. `txHash` is unique (replay protection via DB unique constraint).
7. Payment intent (JWT) binds invoice + payer wallet; sender must match (`invoices.ts:270`).
8. Right token to right wallet but **wrong token** → recorded as `REJECTED` / `TOKEN_MISMATCH`, not silently accepted.

This is good enough for the "real settlement between independent parties" judging bar,
provided the tokens involved are in the verified registry.

## 4. What is deployed where, and how

| Component | Host | Deploy mechanism |
|---|---|---|
| Frontend | Vercel (`celo-desk.vercel.app`) | Vercel's own git integration (no workflow in repo) |
| Backend API | VPS `185.7.81.139` → `https://api.185-7-81-139.sslip.io` | `.github/workflows/deploy-backend.yml` |
| MCP | Same VPS → `https://mcp.185-7-81-139.sslip.io/mcp` | No workflow — manual (not in CI) |
| Telegram bot | Likely same VPS (pm2) | No workflow — manual |

**Backend deploy flow** (`deploy-backend.yml`): triggers on push to `main` touching
`backend/**`. Builds on Ubuntu, then SSHes to the VPS (key from `secrets.VPS_SSH_KEY_B64`),
rsyncs `backend/` (excludes `.env`, `node_modules`, `dist`), runs `npm ci && npm run build`,
`pm2 restart celodesk-api`, health-checks `/health`.

Implications:
- Deploy only fires from **`main`**, not `open-rails`. Our branch work won't deploy until merged (Stage 9).
- A `schema.prisma` change (the tag default) needs a **`prisma migrate deploy`** step on the VPS — the current workflow does **not** run migrations. This must be handled in Stage 4/8.
- MCP and bot have no CI — they'll need a manual restart after changes.

## 6. What breaks if the attribution tag changes

Changing the tag string is **low blast radius** because tagging is centralized:
- Editing `attribution.ts:24` (+ switching to `@celo/attribution-tags`) changes every
  customer payment immediately — no other payment code touches the suffix.
- `schema.prisma:88` default is **cosmetic record-keeping** (stored on the Invoice row for
  audit); it does NOT affect the on-chain suffix, which comes from `attribution.ts`. But it
  should still be updated + migrated so stored records match reality.
- Old invoices already in the DB keep the old tag string in their `attributionTag` column.
  That's fine — it's historical metadata, not replayed on-chain.
- Nothing derives the tag from the repo; it is issued by Loops. So the startup assert
  (Stage 4) should hardcode-check `=== 'celo_3fce81a170fc'`, not compute it.
